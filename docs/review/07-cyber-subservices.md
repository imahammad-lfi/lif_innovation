## Group-level findings

### P1 — Differentiate the four offers without changing the taxonomy

Keep **all four pages**. Do not merge/retire them: they address different enterprise triggers and the client explicitly requires this taxonomy. Assign primary ownership: **AI security & GRC** = AI risk/controls and enterprise evidence; **Cloud security & IAM** = infrastructure/identity controls and hardening; **Exposure validation & AppSec** = authorised external exposure, web/API, code and supply-chain assurance; **Security operations** = ongoing detection, vulnerability workflow and response operating model. Cross-link intersections instead of repeating “AI, LLM & web app testing” and “Controls, IAM & regulation”. Connect AI Code Assurance to quality engineering and Regulated Cyber Readiness to AI/GRC + VajraX, as in the deck. Do not imply five portfolios means every page needs five grids.

### P1 — Turn IP names into visible, credible buying routes

The main content of all four pages contains **no product links**. Navigation has correctly named and valid routes for VajraX, VectorX and AI Governance, but buyers should not need the menu to discover them. Fix **Vector X** in AppSec body, tile and metadata. Use the client-required product wordmarks on white plates and the same teal tile system. Separate **proprietary software**, **reusable accelerators** and **specialist services**; AI Governance is a product, not an accelerator. Explain software licence/subscription separately from project/managed-service commercials. Clarify Linkfields’ own layer around Portkey + Opik and the exact supported integration; do not label upstream open-source tools as Linkfields-owned IP.

### P1 — Evidence and South African accountability are missing

No page names POPIA, a control framework, a delivered evidence artefact or a dated cyber case. Add supported requirements/control mapping with **POPIA as a law, not a certification**, tailored to scope and legal review. ISO control mapping is not organisational certification. The footer renders “ISO Certifications” with an ISO 27001:2022 badge, but image metadata has empty alt text and no certificate URL or scope; the other ISO badge is not self-explanatory. Ask for certificate entity, number, issuer, scope, validity and verification link before using them as credibility proof. Likewise, require actual cyber practitioner qualifications/vendor accreditations before showing badges. B-BBEE Level 1 and South Africa HQ can support procurement/accountability after current documentation is supplied, but do not substitute corporate growth/leadership metrics for security delivery results.

### P1 — Operations must say what is sold and who is accountable

Splunk, Qualys and Rapid7 appear in the deck; that does **not** prove a 24/7 SOC, MDR, vendor partnership, incident retainer or automated interoperability. Obtain the exact model, product modules, analyst staffing/escalation responsibilities, service hours, response authority, reporting and exclusions. Show agreed service measures with definitions rather than inventing MTTR improvements or response SLAs. Make the distinction between sales enquiries and active incidents explicit. Explain processing/access locations for telemetry, source code and AI traces where delivery crosses the global footprint; do not assume all cyber delivery runs from India merely because there is an offshore centre.

### P2 — Preserve the template, change what it communicates

Retain relevant H1/image, short overview, unified teal deliverable tiles and required sticky section navigation. Recommended order: **trigger/outcome → scoped deliverables → applicable IP/baselines → concrete delivery outputs → proof → contextual form**. On Security operations, the operating model comes before capability tiles. Remove the four mid-page generic banners, repeated corporate insights and social strips; additions should replace that space, not create long encyclopaedic pages. Put concise deliverable summaries outside collapsed accordions. Use no generic eight-industry/value-play grid here; link only the relevant value play or related capability.

Desktop is readable and mobile tiles stack well. The inspected mobile pages have `scrollWidth = 390`, matching viewport width; there is no detected whole-page horizontal overflow. The truncated final hero tab is expected horizontal-scroll navigation, not a page overflow defect. One desktop screenshot caught both tab bars during the shot tool’s scroll-to-top transition; a separate settled test confirmed the dock is hidden at the top, visible below the hero and hidden again on returning. **Do not remove or redesign the sticky tabs because of that screenshot artefact.** Compact the long mobile insights/footer journey before adding more content.

All pages render one meaningful H1 and a sensible title; AppSec’s description and keywords need the VectorX naming fix. All rendered canonicals currently point to the **temporary `3001-…manus.computer` hostname**, despite empty page-level `canonicalUrl`. 1. **Service catalogue and boundaries:** supported clouds/IAM vendors, testing types/languages/repositories, Qualys/Rapid7 modules, inclusions/exclusions and assessment versus implementation versus managed-service options.
2. **SOC/operations evidence:** actual model, hours/time zones, analyst roles, location/access arrangements, escalation and containment authority, onboarding, retention and service-measure definitions; approved incident channel only if one exists.
3. **Regulatory and methodology scope:** POPIA responsibilities/data handling/cross-border scope; relevant ISO/NIST/CIS/OWASP/MITRE mapping actually delivered; applicable sector requirements confirmed by the client/legal team. No invented compliance badges or guarantees.
4. **Verified credentials:** current organisational certificates with scope/entity/validity and verification links, practitioner qualifications/vendor partner evidence, current B-BBEE documentation where displayed.
5. **Product proof:** approved VajraX, VectorX and AI Governance screens/wordmarks, product scope/limitations, Linkfields-owned functionality versus upstream tools, actual CI/CD/ticketing/log integrations and standalone licence/subscription options.
6. **Four concise proof examples:** one per service, named with permission or genuinely anonymised, using scope → risk → action → verified output/retest. Any numbers need a baseline, period, measurement method and approved source.
7. **Reusable evidence artefacts:** redacted control-owner-evidence matrix, cloud/access-risk report, authorised testing/retest report, incident playbook/service report; show how accelerators shorten the work without inventing speed metrics.
8. **Conversion content:** approved enquiry response window, scoped assessment/product-walkthrough next steps, secure confidential exchange/NDA process, adjacent privacy notice and explicit separation from active-incident support.

**Not needed:** generic extra FAQs, another full industries grid, unsupported certification/logo walls, alarmist breach statistics, invented client logos, blanket “24/7”, universal “compliance guaranteed”, or recycled corporate performance numbers used as cyber results.
